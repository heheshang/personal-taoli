# B-01 耐久化意图、资金预留与单写者：需求文档

## 1. 文档状态

- 迭代编号：B-01
- 状态：`in_progress`
- 上游：A-01 至 A-05 已实现的只读机会计算与归档；A-05 连续观察延期，未发布
- 下游：B-02 订单事实与 `UNKNOWN` 状态机
- 运行边界：仅 `PAPER` 模式和模拟余额；不得连接真实下单、撤单或私有订单接口

所有者已明确选择先开发、后补 A-05 连续观察。该选择只允许实现无外部副作用的安全交易核心，不解除阶段 A、实盘或真实交易权限门禁。

## 2. 目标与用户可观察结果

系统应在 PostgreSQL 中原子保存一个已批准但尚未发送的双腿执行计划。提交成功时，执行计划、风险决定、双腿订单意图、全部资金预留和审计事件同时可见；失败时全部不可见。共享模拟余额不能被并发计划重复使用。进程断开后，新实例应恢复未终态计划及其预留和 `NOT_SENT` 意图，不自动释放、重建或发送订单。

## 3. 明确不做

- 不连接 Binance、Bybit 或任何真实/测试网下单接口。
- 不实现订单提交、查单、撤单、成交、私有流、`UNKNOWN` 调查或补偿；这些属于 B-02/B-03。
- 不把 PAPER 模拟余额公式用于真实交易所 free/locked 可用额推导。
- 不实现账务、余额对账、控制台、自动主备接管或跨主机 fencing。
- 不申请、读取或要求真实交易凭证。
- 不因 B-01 完成而把 A-05 或阶段 A 标为发布。

## 4. 功能需求

| 编号 | 用户可观察结果 | 验收方法 |
|---|---|---|
| B01-R01 | 初始化 PostgreSQL 后具备版本化 schema，金额列为 `NUMERIC`，关键状态与正数约束由数据库执行 | 在临时 PostgreSQL 执行 migration 并查询 schema 版本 |
| B01-R02 | 同一账户—品种同时只有一个持有执行权的进程；第二实例不能取得资格 | 两个独立连接竞争同一 advisory lock，断言仅一个成功 |
| B01-R03 | 一次调用原子写入 `RESERVED` 计划、批准的风险决定、两条 `NOT_SENT` 意图、预留和审计事件 | 提交后跨表读取；注入余额不足时断言所有业务表无该请求 |
| B01-R04 | 两个不同品种并发竞争同一模拟账户余额时，行锁保证总预留不超过观测 free | 让两个独立单写者并发申请不足以同时覆盖的余额，断言一成一败 |
| B01-R05 | `request_id` 幂等；相同内容返回原计划，不新增行；相同 ID 不同内容失败关闭 | 重复提交并核对行数、计划 ID和错误 |
| B01-R06 | 进程连接断开后，新实例恢复未终态计划、资金预留及两腿 `NOT_SENT` 意图；不自动发送或释放 | 关闭持锁连接，重新取得锁并调用恢复查询 |
| B01-R07 | 预留计划和审计记录包含可追踪 ID、请求摘要、配置/机会引用、账户、品种、场所、资产和时间；数据库 URL 不进入输出 | 检查结构化 PAPER 烟测输出和数据库行 |

## 5. 场景与失败关闭

### 5.1 正常场景

1. PAPER 管理员写入带来源时间的模拟余额。
2. 核心取得账户—品种单写者资格。
3. 调用者提供唯一 `request_id`/`plan_id`、两腿意图和每个场所—资产的明确预留金额。
4. 核心锁定涉及的余额行，确认余额后在单事务中保存完整计划。
5. 返回可恢复的 `RESERVED` 快照。

### 5.2 边界场景

- 相同 `request_id` 和相同规范化内容重复提交，返回第一次结果。
- 两个品种共享同一场所—资产余额，并发时串行检查余额。
- 余额恰好等于申请额时允许预留，之后可用额为零。
- 连接释放后 advisory lock 自动释放，新实例可取得资格。

### 5.3 失败场景

- 未取得单写者资格、字段空白、金额非正、不是恰好两腿、腿/预留重复、账户或品种不匹配：拒绝且不写业务数据。
- 模拟余额不存在、来源时间无效或可用额不足：事务回滚，不产生部分计划。
- 活跃计划已存在：拒绝第二计划，不覆盖旧计划。
- 相同 `request_id` 对应不同摘要：拒绝，不把新请求伪装成成功重试。
- 数据库连接或事务失败：不返回成功，不执行任何外部副作用。

### 5.4 恢复场景

恢复只读取并报告数据库事实：`RESERVED` 计划、`LOCAL_RESERVED` 资金和 `NOT_SENT` 意图保持原值。B-01 不猜测交易所状态，不自动释放预留，不调用模拟或真实下单适配器。

## 6. 数据与安全要求

- 价格、数量、金额使用 `Decimal`/PostgreSQL `NUMERIC`，不经 `f64`。
- 数据库 URL 只从指定环境变量加载，不序列化、不写审计 payload。
- advisory lock 的哈希冲突只能造成保守拒绝，不能让两个写者同时获得同一执行域。
- 资金余额按 `(account_id, venue, asset)` 唯一；并发更新按稳定顺序加行锁，避免重复使用和可避免的死锁。
- 审计事件不可更新或删除；状态物化和审计写入同一事务。
