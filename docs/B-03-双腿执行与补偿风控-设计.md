# B-03 双腿执行与补偿风控：设计文档

文档状态：`released`。当前实现仅覆盖 PostgreSQL/PAPER 事实计算和人工升级决定；没有任何真实或测试网订单副作用。

## 1. 设计结论

B-03 在 B-01 的 `execution_plans`、两腿 `order_intents` 和资金预留，以及 B-02 的订单事实边界之上增加执行事实层。数据库是双腿状态和补偿决定的唯一事实源。B-03 接收已确认的两腿累计成交量，不直接解释订单响应、不直接发订单；它只计算数量差、敞口和预算结果，并将决定作为不可变事实写入数据库。

自动补偿的安全语义是“已计划”，不是“已执行”。只有后续具备独立订单适配器、调用前意图和 UNKNOWN 恢复后，另一个迭代才能消费该决定；当前 `run_paper_smoke("B03")` 固定 `external_order_calls=0`。

## 2. 模块边界

- `crates/core/src/execution.rs`：状态/决定枚举、账户—品种 B-03 单写者、执行事实初始化、事务内评估、事件和补偿决定持久化、PAPER 烟测。
- `crates/core/migrations/0003_double_leg_execution.sql`：`execution_facts` 当前快照、`execution_events` 不可变事件、`compensation_decisions` 决定事实与唯一版本约束。
- `src-tauri/src/commands/paper.rs`：`run_paper_smoke("B03")` 运维入口；在创建 HTTP 客户端和行情适配器前返回。
- `crates/core/src/paper.rs`：提供 B-01 计划和预留；不由 B-03 直接改写余额或释放预留。
- `crates/core/src/order.rs`：上游提供订单/成交事实；B-03 当前直接接受已持久化成交汇总，不访问外部适配器。

## 3. 数据模型与唯一约束

`execution_facts` 以 `plan_id` 为主键，保存目标数量、敞口上限、补偿预算、状态、两腿累计成交、当前差额、当前敞口、累计补偿成本和最后版本。它引用 B-01 `execution_plans`，因此执行计划必须先存在且属于当前账户—品种域。

`execution_events` 保存每次评估的事件类型、版本、时间和 JSON payload；`(plan_id,event_version)` 唯一，且触发器拒绝 UPDATE/DELETE。`compensation_decisions` 保存每次评估的决定、数量、估计成本、原因和创建时间；同样按计划和版本唯一。事件与决定先写入同一事务，随后更新 `execution_facts`，提交失败时全部回滚。

所有金额使用 PostgreSQL `NUMERIC` / Rust `Decimal`。域锁使用 `pg_try_advisory_lock(hash(account_id, instrument_id))`，连接生命周期内持有；数据库行在评估事务中 `FOR UPDATE` 锁定。锁失败直接拒绝第二执行者。

## 4. 状态和决定规则

设 `m = abs(A - B)`，`x = m × exposure_per_unit`，`c = m × compensation_cost_per_unit`：

1. 任一腿超过 `target_quantity`：`MANUAL_REQUIRED`，原因是计划超量。
2. 否则 `m = 0`：`COMPLETED` / `NO_ACTION`。
3. 否则 `x > max_unmatched_exposure`，或累计 `compensation_spent + c > compensation_budget`：`MANUAL_REQUIRED`。
4. 其余情况：`COMPENSATION_PLANNED` / `COMPENSATION_PLANNED`，数量为 `m`。

新的累计成交不得小于当前数据库值；倒退在事务提交前失败。`COMPLETED`、`MANUAL_REQUIRED` 不再评估。当前实现把每次评估的估计成本累加到 `compensation_spent`，即使决定为人工升级，也保留触发预算的事实。

## 5. 事务顺序

1. 取得当前执行域 advisory lock。
2. `initialize_plan` 锁定并校验已存在的 B-01 计划，幂等创建 `PLANNED` 执行事实。
3. `evaluate` 开启事务并 `SELECT ... FOR UPDATE` 当前快照。
4. 校验状态、单调成交和输入非负性；计算差额、敞口、成本与决定。
5. 插入版本化 `execution_events` 和 `compensation_decisions`。
6. 更新 `execution_facts` 的当前状态、成交、差额、成本和版本。
7. 提交事务；再从数据库加载快照返回调用者。

B-03 不在事务内调用网络，不在数据库失败时以内存结果继续，不自动释放 B-01 预留。计划完成后的余额、成交、费用和预留释放由 B-04 对账闭环负责。

## 6. 失败关闭

计划缺失、域不匹配、锁竞争、未知状态、版本/唯一约束冲突、成交倒退、数据库错误均返回错误或人工升级，不产生外部动作。`UNKNOWN` 订单事实必须先由 B-02 查询；B-03 不把“尚未查到”转换成零成交。`MANUAL_REQUIRED` 只表示自动处置停止，控制面必须继续显示可能敞口。

## 8. 安全边界

`run_paper_smoke("B03")` 需要 `TAOLI_DATABASE_URL`，只运行内置确定性 PAPER 场景；输出不包含数据库 URL、密钥或认证请求。它不证明真实撮合、订单恢复、补偿成交、费用或盈利能力，也不改变 A-05 的连续观察发布门槛。
